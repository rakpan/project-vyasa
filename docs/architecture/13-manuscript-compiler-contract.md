# Vyasa Manuscript Compiler Contract

Purpose: define the normative invariants for manuscript assembly in Vyasa. This contract separates editor behavior from compiler behavior and establishes immutable boundaries for citations, sections, visual placeholders, and budgets. This document is authoritative and should be referenced by future code comments.

## Definitions

- Editor: interactive surface where users and agents draft or edit prose blocks. The editor may suggest content but cannot finalize citations, locks, or budgets.
- Compiler: deterministic assembly process that transforms editor drafts, evidence packets, and blueprint structure into a publishable manuscript artifact.
- Canonical Citation Token (CCT): machine-stable token representing a citeable evidence anchor. Vyasa canonical format: `[[chunk:<chunk_id>]]`.
- Rendered Superscript (RS): display-only formatting generated by the compiler from CCTs (e.g., “Text.^[12]”).
- Section Lock: a state marking a section as immutable except for explicitly permitted edits.
- Analytical Note: non-citeable note used to influence framing or style, never evidence.
- Promotion: transition of an Analytical Note from Draft to Manuscript Note after validation.
- VisualPlaceholder: deterministic placeholder for a table/figure/diagram, linked to evidence clusters and blueprint metadata.
- Word Budget: explicit per-section word limit derived from blueprint rules.

## 1) Editor vs Compiler Separation (Normative)

- The editor may generate and revise draft prose, including provisional citation tokens.
- The compiler is the only authority that:
  - Validates and resolves CCTs into RS.
  - Enforces section locking and word budgets.
  - Produces the canonical compiled manuscript artifact.

## 2) Canonical Citation Tokens vs Rendered Superscripts

- CCTs are the only citation representation allowed in drafts.
- RS are compiler-only rendering artifacts and must never be stored in editor drafts.
- CCTs must map to Primary Sources (Evidence) only.
- Analytical Notes may not be cited and must never be assigned CCTs.

## 3) Section Locking Semantics

- A section is lockable once:
  - It is compiled with valid citations and meets word budget.
  - It has passed required integrity checks (citation compliance, evidence coverage).
- Locked sections are immutable except for:
  - Compiler-controlled citation renumbering (RS only).
  - Compiler-controlled formatting and layout decisions.
- Any edit to a locked section must explicitly unlock it and invalidate the compiled artifact for that section.

## 4) Analytical Note Promotion + Staleness Rules

- Draft Notes: editable and influence-only; not eligible for citation.
- Manuscript Notes: promoted only after cross-examination against Evidence Packet A.
- Staleness triggers demotion to Draft when:
  - Underlying Evidence Packet A changes (RetrievalBundle mismatch).
  - The section’s blueprint metadata changes materially (linked RQs, depth intent, visual anchors).
  - The section is unlocked and recompiled.
- Promotion cannot occur if the note introduces facts not grounded in Evidence Packet A.

## 5) VisualPlaceholder Determinism

- VisualPlaceholders must be deterministic from:
  - Blueprint section metadata.
  - Evidence cluster IDs.
  - Visual anchor specifications.
- The compiler must generate identical placeholders for identical inputs.
- Placeholders are immutable once a section is locked.

## 6) Word-Budget Enforcement

- Word budgets are derived from blueprint section rules.
- The compiler enforces word budgets at compilation time.
- Exceeding budget is a compile-time failure; the editor must revise and resubmit.
- The compiler may optionally trim to budget only when explicitly permitted by blueprint rules; otherwise it rejects.

## Allowed / Forbidden Tables

### A) LLM-Generated Content

| Allowed | Forbidden |
| --- | --- |
| Draft prose that references Evidence Packet A via CCTs | Rendered superscripts or final citation numbering |
| Style, analogies, and framing influenced by Analytical Notes | Introducing new factual claims not grounded in Evidence Packet A |
| Provisional section text within a defined word budget | Overriding section locks or budget policies |

### B) Compiler Mutations

| Allowed | Forbidden |
| --- | --- |
| Resolve CCTs into RS | Altering the semantic content of locked prose |
| Enforce word budgets and section locks | Introducing citations to Analytical Notes |
| Deterministic VisualPlaceholder generation | Rewriting editor text without explicit policy |

### C) Immutability Once Locked

| Immutable | Notes |
| --- | --- |
| Locked section prose content | Requires explicit unlock to change |
| Canonical Evidence Packet A reference set | Changes require new RetrievalBundle and recompilation |
| VisualPlaceholders | Locked placeholders cannot be regenerated or mutated |

## Failure Modes and System Responses

- Missing or invalid CCT:
  - Response: compilation fails; editor is notified to fix citations.
- Evidence Packet A absent or mismatched RetrievalBundle:
  - Response: compilation fails; require rerun of retrieval and bundle persistence.
- Analytical Note used as evidence or cited:
  - Response: compilation fails; note is demoted to Draft; section remains unlocked.
- Word budget exceeded:
  - Response: compilation fails; editor must revise or request explicit trimming policy.
- Locked section edited:
  - Response: automatic unlock and invalidation of compiled artifact for that section.
- VisualPlaceholder non-deterministic output:
  - Response: compilation fails; report nondeterminism and block lock.

## Enforcement Summary

- The editor is a drafting surface only. It cannot finalize or mutate compiled artifacts.
- The compiler is the single source of truth for citations, locks, and budgets.
- Once locked, content is immutable unless explicitly unlocked and recompiled.
